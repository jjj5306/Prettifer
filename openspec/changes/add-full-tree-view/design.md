## Context

`Changed Files`는 통합 결과가 건드린 경로만 안다. 결과 밖 파일을 읽는 길은 이미 있다. 심볼 이동이
선택 결과 밖 정의로 갈 수 있어야 해서 `readBaseFile` 계약과 비교 기준 파일을 하나의 문서로 보여
주는 화면이 만들어졌고, renderer는 그것을 `externalFile` 상태로 들고 있다.

없는 것은 목록이다. 비교 기준 커밋에 어떤 경로가 있는지 아무도 조회하지 않는다.

보기 상태는 `useChangedFileView`가 작업대에서 소유한다. `FILE_VIEWS`는 자료로 선언되어 있어 보기
추가가 목록 한 줄이다. Tree View는 `buildFileTree`로 계층을 만들고, `FileTree`는 펼쳐진 폴더의
하위 항목만 렌더링한다. 접힘 집합은 비어 있는 상태로 시작하므로 지금은 모두 펼쳐진다.

## Goals / Non-Goals

**Goals:**

- 비교 기준 시점의 추적 파일 전체를 계층으로 보여 주고 그 안에서 변경 위치를 알 수 있게 한다.
- 변경되지 않은 파일도 비교 기준 내용으로 읽을 수 있게 한다.
- 대형 저장소에서 보기 전환과 스크롤이 쓸 수 있는 상태를 유지한다.
- 이미 있는 비교 기준 파일 읽기 경로를 다시 만들지 않고 쓴다.

**Non-Goals:**

- 파일 검색, 필터, 편집
- `.gitignore` 대상과 untracked 파일
- 변경되지 않은 파일의 diff. 비교할 대상이 없다
- 결과 계산 방식 변경

## Decisions

### 1. 경로 목록은 Full Tree를 처음 열 때 비교 범위당 한 번 조회한다

이슈는 전체 경로 목록을 통합 결과에 포함하기로 적었다. 그대로 하면 완료 기준과 부딪힌다. 목록은
비교 기준 커밋에만 의존하고 선택 커밋과 무관한데, 결과에 실으면 재계산마다 다시 만들어 보내고
Full Tree를 열지 않는 사용자도 그 비용을 낸다.

| 결정 | 이유 |
|---|---|
| 별도 계약으로 조회한다 | 목록은 비교 기준의 성질이다. 결과 계산과 수명이 다르다 |
| Full Tree를 처음 보여 줄 때 조회한다 | 열지 않으면 비용이 0이다 |
| 비교 범위가 그대로면 다시 조회하지 않는다 | 같은 기준 커밋에서 답이 바뀌지 않는다 |
| 범위가 바뀌면 버린다 | 기준 커밋이 바뀌면 목록도 다른 것이 된다 |

`CompositeDiffResultDto`와 `composite-diff-generation`은 손대지 않는다.

### 2. 조회는 커밋을 읽고 작업 트리를 건드리지 않는다

`git ls-tree -r --name-only <기준 커밋>`으로 추적 경로를 얻는다. 커밋을 대상으로 하므로 작업 트리를
읽지도 바꾸지도 않는다. `.gitignore` 대상과 untracked 파일이 결과에 없는 것은 이 명령의 성질이며,
이슈의 제외 범위와 저절로 일치한다.

`readBaseFile`이 `git cat-file`로 같은 커밋에서 파일 하나를 읽는 것과 같은 원리다. 두 읽기가
서로 다른 모듈에 놓이는데, 비교 기준 읽기를 한 모듈로 모으는 일은 이 change의 범위 밖으로 둔다.

### 3. 접힌 상태로 시작하고 변경 파일까지의 길만 펼친다

지금 Tree View는 접힘 집합이 비어 있어 모두 펼쳐진다. 변경 파일 수십 개에는 맞지만 저장소 전체에는
쓸 수 없다. 펼쳐진 폴더의 하위 항목이 모두 렌더링되기 때문이다.

Full Tree는 반대로 시작한다. 모든 폴더를 접고, 변경 파일의 조상 폴더만 펼친다. 그러면 처음 화면에
변경 위치가 바로 보이고, 렌더링되는 행 수는 저장소 크기가 아니라 변경 범위에 따라 정해진다.

이 선택은 Tree View의 접힘 규칙과 반대이므로 두 보기는 접힘 상태를 공유하지 않는다.

### 4. 경로 수에 상한을 두고 넘친 사실을 알린다

접힘으로 초기 렌더링은 묶이지만 계층을 만드는 자료는 전체 경로에 비례한다. 상한을 20,000 경로로
둔다. 그보다 큰 저장소에서 전체 구조를 한 트리에 담는 것은 화면으로서 이미 쓸모가 없고, 상한이
없으면 어디까지 쓸 수 있는지 아무도 모른다.

상한에 걸리면 조용히 자르지 않는다. 표시할 수 있는 범위까지 보여 주고 넘쳤음을 함께 알린다. 심볼
검색이 결과 수 상한에서 하는 것과 같은 방식이다.

### 5. 변경되지 않은 파일은 이미 있는 결과 밖 파일 경로로 보여 준다

선택 결과에 없는 파일을 비교 기준에서 읽어 하나의 문서로 보여 주는 일은 이미 구현되어 있다.
Full Tree에서 변경 없는 파일을 선택하는 것은 그 경로의 또 다른 입구다.

새 상태나 새 계약을 만들지 않는다. 만들면 같은 화면을 두 방식으로 그리게 되고, 둘 중 하나만 고쳐지는
상태가 온다.

### 6. 변경 상태는 결과에서 오고, 변경 없음은 목록에서 온다

트리의 각 파일은 두 자료를 합쳐 상태를 얻는다. 통합 결과에 있는 경로는 그 결과의 추가, 수정, 삭제
또는 문제 상태를 쓴다. 결과에 없는 경로는 변경 없음이다.

삭제된 파일은 기준 커밋에 있으므로 목록에 나온다. 추가된 파일은 기준 커밋에 없으므로 목록에 없고,
결과에서 가져와 트리에 넣어야 한다. 그래서 트리의 경로 집합은 목록과 결과의 합집합이다.

폴더는 하위에 변경 파일이 하나라도 있으면 변경을 품은 폴더로 표시한다. 접힌 상태에서도 그 안을
봐야 할지 판단할 수 있어야 한다.

### 7. 조회 시작은 보기 선택이 알린다

목록을 언제 가져올지 아는 것은 보기 상태이고, 가져오는 것은 컨트롤러다. 보기 상태를 소유한 hook이
Full Tree를 보여 주게 될 때 호출할 함수를 받는다.

컨트롤러가 보기를 알게 하거나, 화면에 effect를 두어 보기 변화를 감시하는 방법도 있다. 전자는 결과
계산만 알던 컨트롤러에 화면 개념을 들이고, 후자는 사용자 동작을 이벤트가 아니라 상태 변화로
되짚는다. 보기를 고르는 그 자리에서 알리는 것이 가장 짧다.

## Risks / Trade-offs

- [상한 아래에서도 큰 저장소는 계층 자료가 크다] → 자료는 한 번 만들고 보기 전환 사이에 유지한다.
  범위가 바뀔 때만 버린다. 상한 도달을 알려 사용자가 무엇을 보고 있는지 알게 한다.
- [변경 없는 파일 내용은 선택 이후 상태가 아니다] → 화면이 선택 결과가 아님을 이미 명시하고 diff
  대신 하나의 문서로 보여 준다. 이 change가 바꾸지 않는다.
- [접힘 규칙이 Tree View와 반대다] → 두 보기가 접힘 상태를 공유하지 않게 하고, 각 보기의 기본
  상태를 요구사항으로 고정한다.
- [Full Tree의 파일 집합이 다른 보기와 다르다] → 다른 세 보기는 변경 파일만 보여 준다는 요구사항을
  유지하고, Full Tree만 변경 없는 파일을 더 보여 준다는 것을 요구사항에 적는다.
