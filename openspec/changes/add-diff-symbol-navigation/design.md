## Context

검토 화면은 Monaco diff editor로 선택 결과를 읽기 전용으로 보여준다. renderer는 파일 시스템과
Git에 접근할 수 없고 preload가 공개한 계약만 호출한다.

이슈 #12는 LSP 프로세스 실행과 프로젝트 전체 빌드 기반 인덱싱을 제외 범위로 두었다. 즉 의미
분석 없이 텍스트 수준에서 정의와 참조를 찾아야 한다.

현재 언어 지원 상태를 먼저 확인했다.

| 언어 | 지금 상태 | Monaco가 주는 것 |
|---|---|---|
| TypeScript, JavaScript | 번들됨 | 언어 서비스(정확한 정의·참조) |
| JSON, CSS, HTML, Markdown | 번들됨 | 심볼 개념이 희박 |
| **Java, C/C++** | **번들 안 됨 → plaintext** | 추가해도 토크나이저(구문 강조)뿐 |

사용자가 실제로 검토하는 대상이 Java와 C/C++이므로, 이 언어들이 1차 대상이다. 두 언어는 구문
강조조차 없던 상태라 함께 추가한다.

## Goals / Non-Goals

**Goals:**

- 검토 화면을 벗어나지 않고 정의와 참조로 이동하고 되돌아온다.
- Java, C/C++, TypeScript, JavaScript를 대상으로 한다.
- 저장소 전체를 검색하되 사용자의 작업 트리를 건드리지 않는다.
- 결과가 확정적이지 않을 때 후보를 숨기지 않고 사용자가 고르게 한다.

**Non-Goals:**

- 코드 편집, 리팩터링
- LSP 프로세스, 빌드 기반 인덱싱
- 검토 화면 밖의 전역 검색 UI
- 타입 기반 오버로드 해석

## Decisions

### 1. 색인을 만들지 않고 `git grep`으로 질의한다

저장소 전역을 대상으로 하려면 색인이 필요하다고 생각하기 쉽지만, 이 저장소에서 측정해 보니
`git grep`이 충분히 빠르다.

```
git grep -n -E "\bCompositeDiffService\b" HEAD   →  43건, 0.116s
```

출력은 `<commit>:<path>:<line>:<내용>` 형식이다. 커밋을 대상으로 검색하므로 작업 트리를 읽지도
바꾸지도 않는다.

색인을 두지 않기로 한 결과 세 가지가 따라온다.

- 색인 수명주기와 무효화가 없다. 저장소가 바뀌어도 다음 질의가 항상 최신이다.
- "인덱싱이 끝나지 않음" 상태가 아예 존재하지 않는다. 이슈의 해당 안내 항목은 검색 실패
  안내로 대체한다.
- 메모리에 저장소 전체를 올리지 않는다.

대안으로 main에서 전체 파일을 읽어 색인을 만드는 방법을 검토했다. 대형 저장소에서 첫 질의까지
지연이 생기고, 색인이 낡지 않게 유지하는 책임이 늘어난다. 얻는 것은 텍스트 검색보다 나은
정확도가 아니라 같은 정확도의 캐시뿐이다.

### 2. 변경 파일은 결과 내용을, 나머지는 비교 기준을 본다

`git grep`은 비교 기준 커밋을 대상으로 한다. 선택 결과에서 변경된 파일은 기준 내용과 다르므로,
그 파일의 검색 결과는 신뢰할 수 없다.

renderer가 이미 선택 결과의 모든 변경 파일 내용을 가지고 있으므로 다음처럼 나눈다.

| 대상 | 검색 주체 | 근거 |
|---|---|---|
| 변경되지 않은 파일 | main (`git grep` on 비교 기준) | renderer는 저장소에 접근할 수 없다 |
| 변경된 파일 | renderer (결과 내용) | 이미 메모리에 있고 IPC가 필요 없다 |

main은 기준 커밋의 결과를 그대로 돌려주고, renderer가 **변경된 경로의 항목을 버린 뒤** 자신이
찾은 결과와 합친다. 그래서 요청에는 변경 경로 목록이 필요 없고 main은 상태를 갖지 않는다.

### 3. 정의 인식은 언어별 선언 패턴으로, 결과는 후보로 제시한다

의미 분석이 없으므로 "정의"는 선언처럼 보이는 줄이다. 언어별 패턴을 자료로 선언하고 순수 함수로
판정한다.

- Java: `class|interface|enum|record` 뒤의 이름, 메서드 선언, 필드 선언
- C/C++: 함수 정의와 선언, `struct|class|enum|typedef` 뒤의 이름, 매크로
- TypeScript/JavaScript: `class|function|const|let|var|interface|type|enum` 뒤의 이름

정확도가 확정적이지 않다는 점을 숨기지 않는다. 후보가 하나면 바로 이동하고, 여러 개면 목록을
보여주고 사용자가 고른다. 오버로드와 같은 이름의 필드가 함께 잡히는 것은 이 방식의 한계이며,
목록으로 드러내는 것이 조용히 한 곳으로 보내는 것보다 낫다.

### 4. 순수 핵심과 얇은 배선으로 나눈다

`src/symbols/`에 순수 모듈을 둔다. 커서 위치의 식별자 추출, 언어 판별, 선언 판정, 출현 위치
추출이 모두 문자열 입력과 값 출력이다. main과 renderer가 같은 모듈을 쓰므로 두 경로의 판정이
어긋나지 않는다.

Monaco에는 자체 제공자를 등록한다. TypeScript는 Monaco 내장 서비스가 더 정확하지만, 내장
서비스는 편집기에 올라온 model만 알기 때문에 저장소 전역을 볼 수 없다. 모든 언어를 같은 경로로
처리해 동작이 일관되게 한다.

## Risks / Trade-offs

- [텍스트 기반이라 정의가 틀릴 수 있다] → 후보를 목록으로 드러내고, 정의로 인식된 항목과 단순
  참조를 참조 목록에서 구분해 표시한다. 사용자가 판단할 재료를 준다.
- [주석과 문자열 안의 출현이 섞인다] → 출현 추출에서 줄 주석과 문자열을 근사적으로 걸러낸다.
  블록 주석의 여러 줄 추적까지는 하지 않으며, 이 한계를 테스트로 고정한다.
- [대형 저장소의 흔한 이름] → `get` 같은 짧고 흔한 이름은 결과가 수백 건이 될 수 있다. 목록에
  상한을 두고, 상한에 걸렸음을 사용자에게 알린다. 조용히 잘라내지 않는다.
- [Monaco 내장 TypeScript 서비스와 동작이 다르다] → 저장소 전역을 보려면 자체 경로가 필요하다.
  일관성을 택한 이유를 위에 남겼다.
