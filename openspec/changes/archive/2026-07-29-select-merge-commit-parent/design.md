## Context

결과 계산은 비교 기준에서 시작한 임시 clone에 선택 커밋을 `cherry-pick --no-commit`으로
차례로 적용한다. 변경 경로는 계산 전에 `diff-tree`로 모아 sparse checkout 범위를 정한다.

두 명령 모두 부모가 하나인 커밋을 전제로 한다. `cherry-pick`은 부모가 둘 이상인
커밋에 기준 부모를 지정하지 않으면 실패하고, `diff-tree`도 merge commit에서는 기본적으로
아무 변경도 출력하지 않는다. 그래서 지금은 이력 조회 단계에서 merge commit을
`selectable: false`로 걸러 아예 선택되지 않게 막고 있다.

선택 상태는 화면에서 커밋 ID 목록으로만 관리하고, main 프로세스에 커밋 ID 배열로
전달한다. 기준 부모를 다루려면 이 계약이 바뀐다.

## Goals / Non-Goals

**Goals:**

- 사용자가 기준 부모를 정하면 merge commit을 통합 결과에 포함한다.
- 기준 부모가 정해지지 않았거나 범위를 벗어나면 계산을 시작하지 않고 안내한다.
- 계산에 사용한 기준 부모를 결과와 화면에 표시한다.
- 기존 선형 커밋 선택 흐름의 동작을 바꾸지 않는다.

**Non-Goals:**

- 두 부모의 변경을 동시에 반영하는 계산.
- 부모가 셋 이상인 octopus merge에 대한 최적화. 계약은 지원하되 별도 흐름은 두지 않는다.
- 기준 부모를 시스템이 추천하거나 자동 선택하는 동작.
- 조상 관계가 없는 커밋의 적용 순서 확인 (#18에서 다룬다).

## Decisions

### 결정 1: 기준 부모는 1부터 시작하는 부모 번호로 다룬다

Git의 `cherry-pick -m <n>`과 `diff-tree <parent> <commit>`이 모두 부모 순서를 기준으로
동작하므로, 기준 부모를 부모 번호로 표현한다. 부모 커밋 ID를 직접 받지 않는다.

- **근거**: Git 명령과 표현이 1:1로 대응해 변환 실수가 생기지 않는다. 부모 목록은
  이력 조회가 이미 `parentIds`로 제공하므로 화면이 번호와 커밋 ID를 함께 보여줄 수 있다.
- **대안**: 부모 커밋 ID를 받고 내부에서 번호로 변환 → 같은 커밋이 두 번 부모로 오는
  경우를 다뤄야 하고 검증이 늘어나 기각.

### 결정 2: 기준 부모는 커밋 ID를 키로 하는 조회 자료로 전달한다

선택 커밋은 지금처럼 커밋 ID 배열로 두고, 기준 부모를 커밋 ID를 키로 하는 별도
자료(`mainlineParents`)로 함께 전달한다.

- **근거**: 이 자료는 선택 목록과 나란히 놓인 두 번째 목록이 아니라 선택 목록의
  원소를 키로 쓰는 조회표다. 순서를 맞출 필요가 없어 어긋날 수 없고, 선택되지 않은
  커밋의 항목은 무시하면 되고, merge commit에 항목이 없는 상태가 곧 "기준 부모
  미지정"이라 따로 표현할 값이 필요 없다.
- **대안**: 선택 커밋을 `{ id, mainlineParent? }` 값 객체 배열로 바꾸는 방식.
  개념상 (커밋, 기준 부모)를 한 자료로 묶는 것이 더 정확해 처음에는 이 안을 택했다.
  그러나 코어, 공유 계약, main, 화면과 기존 테스트의 모든 호출부가 함께 바뀌는데
  검증 로직은 어느 쪽이든 동일해서 실익이 없다. 부모가 하나인 커밋만 다루는 호출부가
  대부분이므로 그쪽 계약을 그대로 두는 편이 변경 범위가 작고 읽기도 쉽다. 기각.
- **#27의 이중 구조 문제와 다른 점**: #27에서 정리하는 `MutableDirectory`는 같은
  대상을 배열과 맵에 **중복 저장**해 삽입 시 두 곳을 함께 갱신해야 했다. 여기서는
  기준 부모가 한 곳에만 저장되고 커밋 ID로만 연결된다.

화면 상태도 체크 상태(`selectedCommitIds`)와 기준 부모 선택(`mergeParents`)을 분리해
유지한다. 두 값은 서로 다른 사용자 동작에서 나온다.

### 결정 3: 변경 경로는 기준 부모와 커밋을 비교해 얻는다

merge commit의 변경 경로를 `diff-tree --no-commit-id --name-only -r -z <기준부모> <커밋>`
으로 얻는다. 부모가 하나인 커밋은 지금처럼 `diff-tree ... <커밋>`을 쓴다.

- **근거**: 기준 부모와 커밋을 직접 비교하면 `cherry-pick -m`이 실제로 적용하는 변경과
  같은 범위가 나온다. sparse checkout 범위와 적용 결과가 어긋나지 않는다.
- **대안**: `diff-tree -m` 또는 `--first-parent` → 기준 부모가 첫 부모가 아닌 경우
  범위가 달라져 기각.

### 결정 4: 기준 부모 검증은 선택 계획 단계에서 한다

기준 부모 번호가 그 커밋의 부모 수 안에 있는지, merge commit에 기준 부모가 지정되었는지를
선택 계획 단계에서 확인하고 기존 선택 오류와 같은 방식으로 알린다.

- **근거**: 계산을 시작해 임시 clone을 만든 뒤 실패하는 것보다 이르게 막는 편이
  사용자에게 빠르고 정리할 자원도 없다. 기존 `SelectionError` 흐름을 재사용해 화면의
  진단 표시 경로가 그대로 동작한다.

### 결정 5: 이력 조회는 merge commit을 선택 가능으로 표시한다

`selectable`을 `!isMerge`에서 "비교 범위 안에 있는 커밋"으로 바꾼다. `isMerge`와
`parentIds`는 그대로 제공해 화면이 기준 부모 선택 수단을 표시할 수 있게 한다.

- **근거**: 선택 가능 여부와 "추가 정보가 필요한지"는 다른 개념이다. 후자는 화면이
  `isMerge`로 판단한다.

## Risks / Trade-offs

- 계약 변경이 화면과 main 프로세스에 동시에 영향 → 공유 스키마를 먼저 바꾸고
  타입 검사로 누락된 호출부를 드러낸 뒤 순서대로 고친다.
- merge commit 적용은 충돌 가능성이 부모가 하나인 커밋보다 높다 → 기존
  `COMMIT_APPLY_CONFLICT` 안내가 그대로 동작하는지 통합 테스트로 확인한다. 파일별
  부분 결과는 이 범위가 아니며 #16에서 다룬다.
- 기준 부모를 잘못 고르면 의도와 다른 결과가 나온다 → 결과에 사용한 기준 부모를
  표시해 사용자가 확인할 수 있게 한다.
- octopus merge에서 부모 번호가 3 이상일 수 있다 → 번호 범위를 부모 수로 검증하고
  특별한 분기를 두지 않는다.
