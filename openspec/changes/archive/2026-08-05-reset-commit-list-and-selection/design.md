## Context

비교 범위를 불러오면 첫 페이지가 `range.commits`에 담기고 `range.nextOffset`이 다음 페이지의
시작을 가리킨다. `Load 100 older commits`는 `range/page-loaded`로 새 페이지를 **덧붙인다**.
그래서 목록은 늘어나기만 하고 줄어드는 길이 없다.

선택은 `selectedCommitIds`와 `mergeParents`에 있다. 커밋 하나의 체크를 되돌리는 길은 있지만
전체를 비우는 길은 없다.

페이지 크기 100은 main의 `listCommits`에만 있고 renderer는 모른다.

## Goals / Non-Goals

**Goals:**

- 불러온 커밋을 첫 페이지 상태로 되돌린다.
- 선택을 한 번에 비운다.
- 두 초기화가 서로의 상태를 건드리지 않는다.
- 초기화가 실패할 수 있는 동작이 되지 않게 한다.

**Non-Goals:**

- 비교 범위 초기화. `Load Commit Range`가 이미 한다
- 되돌리기 이력과 다시 실행
- 선택 저장과 복원
- 페이지 크기 변경

## Decisions

### 1. 불러온 커밋 초기화는 저장소를 다시 읽지 않는다

첫 페이지를 다시 요청하는 방법을 먼저 검토했다. 언제나 정확한 답을 얻지만 두 가지가 걸린다.

| 문제 | 내용 |
|---|---|
| 실패할 수 있다 | 목록을 줄이는 사소한 동작이 진단을 띄울 수 있다 |
| 기다려야 한다 | 이미 화면에 있는 자료를 버리는 일에 왕복이 생긴다 |

renderer는 이미 필요한 것을 다 갖고 있다. 페이지는 순서대로 덧붙으므로 첫 페이지는 배열의 앞부분
그대로다. 그래서 초기화는 앞부분만 남기고 자르는 일이다. 실패할 수 없고 즉시 끝난다.

### 2. 자르는 경계는 첫 페이지를 불러올 때 기억한다

앞에서 몇 개를 남길지 알아야 한다. renderer에 100을 적으면 페이지 크기 결정이 main과 renderer 두
곳에 생긴다. 한쪽만 바뀌는 상태가 온다.

대신 비교 범위를 불러온 직후의 `nextOffset`을 기억한다. 그 값이 곧 첫 페이지에 담긴 커밋 수다.
페이지 크기가 바뀌어도 renderer는 고칠 것이 없다.

첫 페이지가 마지막 페이지면 `nextOffset`은 null이고, 그때는 되돌릴 것이 없으므로 초기화를 두지
않는다.

### 3. 두 초기화는 자기 상태만 건드린다

불러온 커밋 초기화는 `commits`와 `nextOffset`만 바꾼다. 선택은 그대로 둔다. 잘려 나간 커밋을
선택해 두었더라도 선택은 유지한다. 목록을 줄이는 것과 결과에서 빼는 것은 다른 일이고, 사용자가
요청한 것은 앞쪽이다.

선택 초기화는 `selectedCommitIds`와 `mergeParents`를 비운다. 커밋 하나의 체크를 되돌릴 때와 같이
계산된 결과와 선택 파일도 함께 내려놓는다. 선택이 사라진 결과를 현재 결과로 두면 화면이 어긋난다.

### 4. 되돌릴 것이 없으면 컨트롤을 두지 않는다

첫 페이지만 불러온 상태에서 목록 초기화는 아무것도 하지 않는다. 선택이 없을 때 선택 초기화도
아무것도 하지 않는다. 눌러도 변화가 없는 컨트롤을 두면 사용자가 상태를 잘못 읽는다.

비활성으로 두는 방법도 있지만, 이 화면의 `Load 100 older commits`는 더 불러올 것이 없으면 사라진다.
같은 규칙을 따른다.

## Risks / Trade-offs

- [잘린 커밋이 선택에 남아 화면에서 안 보인다] → 선택 개수는 계속 표시되고, 결과 머리글이 포함된
  커밋 수를 따로 보여 준다. 다시 불러오면 그 커밋이 체크된 상태로 나타난다. 선택을 조용히 버리는
  것보다 낫다.
- [초기화가 늘어 머리글이 붐빈다] → 되돌릴 것이 있을 때만 나타나므로 평소에는 지금과 같다.
- [`nextOffset`을 기억하는 필드가 상태에 하나 늘어난다] → 페이지 크기를 renderer가 다시 정의하지
  않기 위한 값이다. 범위를 불러올 때 한 번 정해지고 그 뒤 바뀌지 않는다.
