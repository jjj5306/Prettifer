## Context

Prettifer 저장소에는 사용자 경험을 정의한 OpenSpec과 초기 목업만 있으며 실행 가능한 코어는 아직 없다. 첫 구현은 기준 브랜치에서 갈라진 선형 이력을 대상으로, 비연속 커밋 선택이 만든 최종 상태를 실제 Git 의미에 맞게 계산해야 한다.

계산 과정은 사용자의 현재 브랜치, staged 변경, unstaged 변경과 untracked 파일을 건드리지 않아야 한다. 이후 VS Code 확장과 다른 연동 수단이 같은 코어 동작을 사용할 수 있도록 Git 실행, 합성 절차와 결과 게시 책임을 분리한다.

## Goals / Non-Goals

**Goals:**

- 선택과 독립적인 비교 기준에서 선택 커밋만 반영된 최종 상태를 계산한다.
- 선형 이력의 비연속 커밋과 같은 파일에 누적된 선택 변경을 지원한다.
- 실제 Git 동작을 사용하는 재현 가능한 자동화 테스트로 사용자 계약을 보호한다.
- 성공, 실패와 취소 후 사용자 작업 상태를 보존한다.
- 동시에 요청된 계산이 서로 영향을 주지 않으며 최신 선택의 결과만 게시한다.
- Git 실행 방식과 합성 작업 공간을 교체 가능한 경계에 둔다.

**Non-Goals:**

- 조상 관계로 순서를 정할 수 없는 여러 브랜치의 커밋
- merge commit의 기준 부모 선택과 루트 커밋 비교
- 충돌 파일의 제외, 부분 결과와 자동 복구
- rename 추론과 binary 파일 내용 표현
- 전체 Git 그래프, VS Code 화면과 좌우 diff 화면
- 파일 이력과 경로·확장자 기반 그룹화
- 공개 API, CLI, 배포와 수익화 기능

## Decisions

### TypeScript 기반 코어

코어는 지원되는 Node.js 환경에서 실행되는 TypeScript 프로젝트로 시작한다. VS Code 확장과 같은 언어 및 실행 환경을 공유해 초기 통합 비용을 낮추고, 타입 검사와 작은 모듈 경계로 계약을 보호한다. 코어의 도메인 동작은 편집기 API에 의존하지 않는다.

### 실제 Git 실행을 경계에 배치

저장소 탐색과 변경 적용은 설치된 Git 실행 파일을 사용하며, 프로세스 실행과 Git 명령 구성은 전용 경계에서 담당한다. Git의 patch 적용, 경로 처리와 diff 의미를 그대로 검증할 수 있고 도메인 흐름을 프로세스 및 파일 시스템 세부사항과 분리할 수 있다.

모든 Git 호출은 인자 배열로 실행하고 pager, 색상, 외부 diff와 대화형 입력을 비활성화한다. 종료 코드, 표준 오류와 취소 신호는 손실 없이 상위 흐름에 전달한다.

### 명시적인 비교 기준과 선택 검증

계산 요청은 기준 브랜치와 현재 작업 브랜치의 공통 조상을 비교 기준으로 확정한다. 확정된 기준은 선택 변경과 무관하게 유지한다. 선택 커밋은 비교 기준의 후손이며 하나의 조상 관계로 정렬할 수 있는지 검증한 뒤 오래된 커밋부터 처리한다.

선택하지 않은 커밋은 비교 기준이나 초기 파일 상태에 포함하지 않는다. 이 규칙은 선택된 변경만 포함된다는 사용자 계약을 보호한다.

### 요청별 임시 작업 공간에서 합성

각 계산은 비교 기준을 가리키는 분리된 임시 Git 작업 공간을 생성한다. 선택 커밋의 변경을 확정된 순서로 커밋 생성 없이 적용하고, 비교 기준과 완성된 작업 공간 사이에서 최종 파일 상태와 통합 diff를 계산한다.

임시 작업 공간의 생성, 변경 적용과 제거는 하나의 수명 주기로 관리한다. 정상 완료, Git 오류와 취소 경로 모두 정리 절차를 실행하며 사용자 작업 디렉터리에서는 변경 명령을 실행하지 않는다. 이 책임은 별도 경계에 두어 이후 더 적합한 격리 방식으로 교체할 수 있게 한다.

### 최신 요청만 결과로 게시

선택이 바뀔 때마다 계산 세대를 증가시킨다. 완료된 계산은 자신의 세대가 현재 세대와 같을 때만 현재 결과가 된다. 이전 계산은 취소를 요청하고, 취소가 늦게 완료되더라도 새 선택의 결과를 덮어쓸 수 없다.

### 재현 가능한 결과

파일과 변경 항목은 경로를 기준으로 안정적으로 정렬한다. Git 출력에 환경별 색상, pager와 외부 변환을 사용하지 않으며 동일한 입력에서 달라질 수 있는 임시 경로와 실행 시각을 결과에 포함하지 않는다.

### 실제 저장소 fixture를 사용하는 TDD

테스트는 임시 Git 저장소를 만들고 의미 있는 커밋 메시지와 고정된 별칭으로 이력을 구성한다. 각 요구사항은 실패하는 인수 테스트로 먼저 표현하고 최소 구현, 구조 개선, 전체 회귀 검증 순서로 진행한다.

fixture에는 다음 흐름을 포함한다.

- 기준 커밋 이후 로그인 검증, 내부 리팩터링, 세션 저장과 문서 변경이 이어지는 선형 이력
- 로그인 검증과 세션 저장처럼 서로 떨어진 커밋 선택
- 하나의 인증 파일을 두 선택 커밋이 순차적으로 변경하는 이력
- 파일 추가, 수정과 삭제
- staged, unstaged와 untracked 변경이 함께 있는 사용자 작업 상태

## Risks / Trade-offs

- [선택 변경이 미선택 변경의 문맥에 의존해 정상 합성 범위를 벗어남] → 지원 범위 판정과 진단 경계를 유지하고 부분 결과 동작은 별도 change에서 검증한다.
- [프로세스 중단으로 임시 작업 공간의 관리 정보가 남음] → 모든 종료 경로에서 정리를 실행하고 시작 시 안전하게 식별되는 잔여 작업 공간만 정리한다.
- [Windows에서 잠긴 파일 때문에 즉시 정리가 실패함] → Git 프로세스 종료를 확인한 뒤 제한된 재시도를 수행하고 남은 경로를 진단 정보에 포함한다.
- [로컬 Git 버전과 설정에 따른 출력 차이] → 필요한 설정을 명령 단위로 고정하고 지원 범위를 자동화 테스트에서 검증한다.
- [큰 저장소에서 작업 공간 생성과 적용 시간이 증가함] → 요청별 취소를 지원하고 실행 단계별 시간을 측정할 수 있는 경계를 유지한다.
