## Context

선언 판정은 언어별 정규식 목록이고, 맞으면 `isDeclaration: true` 하나만 남긴다. 그래서 화면은
"선언처럼 보이는 줄"과 "그 줄이 무엇을 선언하는지"를 구분할 수 없다.

같은 이름을 여러 종류가 선언하는 것은 예외가 아니라 Java의 일상이다.

```java
public class UtVar {          // 형 선언
    public UtVar() {}         // 생성자
    public UtVar(int seed) {} // 생성자 오버로드
}
```

`UtVar`의 선언은 셋이며, 어느 것을 원하는지는 코드만 봐서는 알 수 없다. 누른 자리를 보면 알 수 있다.

## Goals / Non-Goals

**Goals:**

- 후보가 무엇인지 화면에서 구분된다.
- 누른 자리가 말해 주는 것을 쓴다. `new` 뒤면 생성자다.
- 놓치던 선언을 잡되 거짓 양성을 늘리지 않는다. 실측으로 증명한다.

**Non-Goals:**

- 의미 분석, 형 해석, 스코프 추적. 여전히 텍스트 수준이다.
- 오버로드 해석. 인자 개수와 형으로 고르지 않는다. 여러 개면 사용자가 고른다.
- 상속 계층을 따라가는 멤버 해석.

## Decisions

### 1. 판정 결과를 boolean에서 종류로 바꾼다

`declaresSymbol(...): boolean`을 `declarationKindOf(...): DeclarationKind | null`로 바꾼다.
`isDeclaration`은 `kind !== null`과 같은 말이므로 계약에서 없애고 `kind`만 남긴다. 같은 사실을
두 자리에 두면 어긋난다.

| 종류 | 무엇 | 예 |
|---|---|---|
| `type` | 형 선언 | `public class UtVar {`, `struct Node {`, `interface Store {` |
| `constructor` | 생성자 | `public UtVar(int seed) {` |
| `method` | 메서드·함수 | `public int total() {`, `int main(void) {` |
| `field` | 형의 멤버 변수 | `private String userCode;` |
| `variable` | 지역 변수·`const`·`let` | `int userCode = 3;` |
| `alias` | 별칭 | `typedef int Handle;`, `type Id = string;` |
| `macro` | 매크로 | `#define MAX 10` |

패턴은 종류별로 묶어 선언한다. 한 줄이 여러 패턴에 맞을 수 있으므로 **표의 위에서 아래 순서로**
처음 맞는 것을 쓴다. 생성자 패턴이 메서드 패턴보다 앞이면 `public UtVar() {`이 메서드로 잡히지
않는다.

### 2. 누른 자리의 맥락은 한 가지만 본다: `new`

맥락 판정을 늘릴수록 틀릴 여지가 커진다. 실제로 값을 하는 것 하나만 본다.

- 커서 왼쪽에 `new`가 (공백만 사이에 두고) 있으면 `construction`.
- 그 밖에는 `plain`.

`construction`이면 생성자를, `plain`이면 형 선언을 우선한다. 판정은 어댑터가 이미 가진 그 줄의
문자열로 하며, 클릭 대상을 찾는 `symbolAt`과 같은 입력을 쓴다.

### 3. 우선순위는 정렬이 아니라 "가장 높은 종류만 후보"로 쓴다

정의 이동에서 후보를 종류로 걸러낸다.

| 맥락 | 우선순위 |
|---|---|
| `construction` | `constructor` → `type` → 나머지 |
| `plain` | `type` → `method` → `field` → `alias` → `macro` → `variable` → `constructor` |

가장 높은 순위에 후보가 하나면 바로 이동한다. 여러 개면(오버로드, 같은 이름의 클래스 둘) 그 종류의
후보만 목록으로 보여 준다. 낮은 순위의 후보는 목록에서도 뺀다. 남기면 `total`을 찾을 때 저장소
곳곳의 지역 변수가 섞여 목록이 쓸모없어진다.

`plain`에서 `constructor`를 맨 뒤에 두는 이유: 생성자를 원했다면 `new` 옆을 눌렀을 것이다. 형
선언이 있는데 생성자로 보내면 거의 항상 틀린다.

참조 목록(Shift+F12)은 걸러내지 않는다. 참조 목록의 목적은 전부 보여 주는 것이다.

### 4. 놓친 패턴은 애너테이션과 수정자 요구를 풀어서 고친다

| 놓친 줄 | 원인 | 조치 |
|---|---|---|
| `@Override public int total() {` | 줄 시작 뒤 바로 수정자를 요구 | 애너테이션(`@Name(...)`) 접두를 허용 |
| `String userCode;` | 필드에 수정자를 최소 하나 요구 | 형 + 이름 + `=`/`;`로 충분하게 하되, 아래 방어를 둔다 |
| `int userCode = 3;` | 같은 이유 | 같은 패턴이 지역 변수도 잡는다. 종류로 구분해 우선순위에서 뒤로 보낸다 |

수정자 요구를 풀면 `return userCode;`나 `foo(a, b);` 같은 줄이 잡힐 위험이 생긴다. 그래서 형 자리에
올 수 없는 것을 막는다.

- 줄이 제어 키워드(`return`, `if`, ...)로 시작하면 선언이 아니다.
- 이름 앞의 형 자리 토큰이 하나여야 한다. `this.userCode = 4;`처럼 점이 낀 좌변은 제외한다.
- 이름 뒤가 `=` 또는 `;`여야 한다.

이 조건들이 실제로 거짓 양성을 막는지는 코퍼스로 확인한다. 코퍼스는 테스트에 그대로 남겨, 나중에
패턴을 건드릴 때 무엇을 깨뜨렸는지 즉시 드러나게 한다.

## Risks / Trade-offs

- [종류 판정이 틀리면 우선순위가 틀린 곳으로 보낸다] → 후보가 하나일 때만 바로 이동하고, 목록에는
  종류를 그대로 표시한다. 사용자가 판단할 재료를 계속 준다.
- [낮은 순위 후보를 목록에서 빼면 진짜 대상을 숨길 수 있다] → 높은 순위에 후보가 없으면 다음
  순위로 내려가므로, 무엇도 남지 않는 경우에만 "찾지 못함"이 된다.
- [`new` 판정은 한 줄만 본다] → 여러 줄에 걸친 `new\n    UtVar(...)`는 놓친다. 놓치면 형 선언으로
  가며, 그때도 목록에 생성자가 남지 않을 뿐 이동 자체는 유효하다.
- [코퍼스가 실제 코드를 대표하지 못할 수 있다] → 실제 Java 관용구(애너테이션, 제네릭, throws,
  오버로드, 빌더 호출)를 넣어 41개로 시작하고, 새 결함이 보고되면 줄을 추가한다.
