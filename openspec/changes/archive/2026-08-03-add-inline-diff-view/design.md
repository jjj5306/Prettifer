## Context

diff는 Monaco의 diff editor로 그린다. Monaco는 `renderSideBySide` 옵션으로 좌우와 인라인을 모두
지원하므로, 이 기능에서 새로 만들 것은 배치 로직이 아니라 **전환 경로**다.

이슈 #61에서 얻은 것이 바로 여기에 쓰인다. 편집기를 다시 만들면 스크롤이 맨 위로 돌아간다. 보기
전환은 사용자가 지금 보고 있는 줄을 유지해야 하므로, 재생성이 아니라 옵션 갱신이어야 한다.

## Goals / Non-Goals

**Goals:**

- 좌우와 세로를 전환할 수 있고, 현재 보기가 화면과 보조 기술에 드러난다.
- 전환이 보고 있던 위치와 선택 파일을 유지하고 새 계산을 일으키지 않는다.
- 키보드만으로 전환할 수 있다.

**Non-Goals:**

- 단어 단위 강조 방식 변경.
- 세로 보기 전용 기능. 두 보기 모두 읽기 전용이라는 점은 그대로다.
- 보기 선택을 저장소나 세션 밖으로 저장하는 일. 설정 영속화는 이 저장소에 아직 없다.

## Decisions

### 1. 전환은 `updateOptions`로만 한다

`editor.updateOptions({ renderSideBySide })`는 model을 유지하므로 스크롤, 커서, 접힘 상태가 그대로
남는다. 어댑터에 `setView(view)`를 두고, 편집기를 만들 때도 같은 값을 초기 옵션으로 넘긴다.

재생성으로 구현하면 코드가 더 짧지만(그저 `currentKey`에 보기를 넣으면 된다) 이슈의 완료 기준
"전환 뒤 diff 맥락이 유지되고 새 계산이 발생하지 않는다"를 어긴다. 이슈 #61이 정확히 그 증상이었다.

### 2. 보기 선택은 검토 화면의 지역 상태로 둔다

Tree/List 토글도 `ChangedFilePane`의 지역 상태다. 같은 성격이므로 같은 자리에 둔다. 계약이나
reducer를 건드리지 않으니 main과 preload는 이 기능을 모른다.

결과를 다시 만들면 검토 화면이 사라지고 보기 선택도 초기값으로 돌아간다. Tree/List와 같은 수명이며,
그보다 오래 남기려면 설정 영속화가 필요하다. 그것은 이슈 #13의 범위다.

### 3. 좁은 화면에서 자동으로 세로로 바꾸지 않는다

이슈는 "좁은 화면에서 기본 보기를 세로로 둘지 판단해 적용한다"고 남겼다. 판단 결과는 **자동 전환을
두지 않는다**.

- 창 크기를 조절하는 것만으로 사용자가 고른 보기가 뒤집히면, 고른 적이 없는 상태로 되돌아간다.
- 같은 화면의 Tree/List 토글도 폭에 따라 자동으로 바뀌지 않는다. 한 화면에서 두 토글이 다르게
  행동하면 규칙을 배울 수 없다.
- 좁은 화면에서 세로가 낫다는 판단 자체는 사용자가 즉시 내릴 수 있고, 토글이 바로 옆에 있다.

기본값은 좌우다. 지금까지의 유일한 보기이므로, 기본을 바꾸면 이 기능을 원하지 않은 사용자의 화면도
바뀐다.

### 4. 비교할 기준이 없는 화면에는 토글을 두지 않는다

추가된 파일, 선택 결과 밖 파일, 문제 파일, 바이너리는 문서 하나 또는 안내문이다. 좌우로 나눌 것이
없으므로 토글이 있어도 아무 일도 하지 않는다. 눌러도 반응 없는 컨트롤을 두는 대신, 적용되는 화면에만
나타나게 한다.

## Risks / Trade-offs

- [보기가 결과를 다시 만들면 초기화된다] → Tree/List와 같은 수명이라 일관되다. 더 오래 남기려면
  설정 영속화가 선행되어야 하며, 그 이유를 위에 남겼다.
- [토글이 파일에 따라 나타나고 사라진다] → 적용되지 않는 화면에서 컨트롤을 보여 주는 것보다 낫다고
  판단했다. 어떤 화면에서 사라지는지는 스펙에 시나리오로 남긴다.
- [Monaco 인라인 보기의 세부 표현은 우리가 정하지 않는다] → 삭제와 추가를 한 흐름으로 잇는다는
  요구를 Monaco가 이미 만족한다. 우리가 검증할 것은 옵션이 실제로 그 값으로 갱신되는지다.
