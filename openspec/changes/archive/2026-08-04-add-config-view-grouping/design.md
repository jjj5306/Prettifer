## Context

`Changed Files`는 renderer의 `ChangedFilePane`이 통합 결과(`CompositeDiffResultDto`)만 받아
Tree View와 List View를 그린다. 보기 선택과 폴더 접힘 상태는 컴포넌트 지역 상태이며, 앱을 다시
실행하면 사라진다. 지금 이 저장소에는 사용자 설정을 보관하는 경계가 하나도 없다.

renderer는 파일 시스템과 Git에 접근할 수 없고 preload가 공개한 계약만 호출한다. 기존 계약은 모두
검토 대상 저장소를 읽는 요청이고, 무언가를 **쓰는** 요청은 아직 없다.

이슈 #13은 규칙 저장 위치를 이 change에서 확정하도록 남겼다. 동시에 이슈는 "팀 설정 동기화"를 제외
범위로 두었고, 기존 요구사항은 "검토 전후 사용자 branch, HEAD와 작업 트리가 동일해야 한다"를
유지한다. 이 두 제약이 저장 위치 결정을 좁힌다.

## Goals / Non-Goals

**Goals:**

- 사용자가 자기 저장소의 경로 prefix 규칙을 정의하고 그 규칙대로 변경 파일을 묶어 본다.
- 규칙을 저장소별로 분리해 보관하고 앱을 다시 실행해도 복원한다.
- 규칙이 겹치거나 잘못되어도 결과를 감추지 않는다. 묶을 수 있는 만큼 묶고 원인을 안내한다.
- 어떤 규칙에도 걸리지 않은 파일이 사라지지 않는다.
- 보기 전환이 통합 결과 재계산이나 Git 요청을 발생시키지 않는다.

**Non-Goals:**

- 정규식과 glob, 확장자 기반 규칙
- 중첩 그룹
- 그룹별 일괄 작업(승인, 무시)
- 규칙을 팀과 공유하는 동기화
- 내장 기본 규칙 세트 제공

## Decisions

### 1. 규칙은 앱 사용자 데이터에 보관하고 저장소 루트 경로로 나눈다

검토 대상 저장소 안에 설정 파일을 두는 방법을 먼저 검토했다. 팀과 공유하기 쉽지만 Prettifer가
사용자의 작업 트리에 파일을 만들게 된다. "검토 전후 저장소 상태가 동일하다"는 기존 요구사항과 정면으로
충돌하고, 얻는 이점인 공유는 이 이슈의 제외 범위다.

그래서 규칙은 앱 사용자 데이터 디렉터리의 파일 하나에 보관하고, 저장소별 항목으로 나눈다.

| 결정 | 이유 |
|---|---|
| 저장소 밖, 앱 사용자 데이터에 보관한다 | 검토 대상 저장소를 건드리지 않는다 |
| 저장소 루트의 정규화된 절대 경로를 키로 쓴다 | 세션이 이미 가진 값이고, remote가 없는 저장소에서도 동작한다 |
| 파일 하나에 모든 저장소 항목을 담는다 | 규칙은 작고 수가 적다. 파일이 흩어질수록 진단이 어려워진다 |
| 읽기와 쓰기를 main 경계에 둔다 | renderer는 파일 시스템에 접근하지 않는다는 기존 구조를 유지한다 |

키를 remote URL이나 최초 커밋 해시로 잡는 대안도 검토했다. remote가 없거나 바뀌는 저장소가 있고,
같은 저장소를 여러 경로에 clone해 두고 서로 다른 규칙을 쓰고 싶을 수도 있다. 경로 키가 사용자가
예측하기 쉽고, 경로가 바뀌면 규칙이 비어 보인다는 한계는 안내로 드러낸다.

### 2. 그룹화는 순수 함수이고 renderer에서 계산한다

그룹화 입력은 변경 파일 경로 목록과 규칙 목록뿐이다. 둘 다 renderer가 이미 가지고 있으므로 그룹화에
IPC도 Git도 필요 없다. `(경로 목록, 규칙 목록) → 그룹 목록`을 순수 함수로 두면 보기 전환이 새 요청을
만들지 않는다는 요구사항이 구조로 보장되고, 경계 조건을 함수 단위 테스트로 고정할 수 있다.

main이 맡는 일은 규칙을 읽고 쓰는 것뿐이다. main은 그룹화를 알지 못한다.

### 3. prefix는 경로 세그먼트 경계에서만 일치시킨다

`src/te`가 `src/test.txt`를 잡으면 사용자가 의도하지 않은 그룹이 생긴다. prefix는 디렉터리 경로로
해석하고, 경로 세그먼트 경계에서만 일치시킨다. 저장 시 앞뒤 `/`를 정규형으로 맞추고, 비교는
정규화된 저장소 상대 경로끼리 한다.

경로 구분자는 `/`만 쓴다. 통합 결과의 파일 경로가 이미 저장소 상대 경로이며 `/`로 구분된다.

### 4. 겹치면 가장 긴 prefix, 표시 순서는 사용자가 정한다

`src/`와 `src/test/`가 모두 정의되면 `src/test/a.java`는 `src/test/`에 들어간다. 사용자 정의 순서를
우선하면 규칙을 추가할 때마다 기존 파일이 다른 그룹으로 조용히 옮겨 갈 수 있다. 가장 긴 prefix는
규칙 목록의 순서와 무관하므로 결과가 순서에 흔들리지 않는다.

같은 길이로 겹치는 경우, 즉 prefix가 완전히 같은 규칙 둘은 검증에서 막는다. 그래서 적용 규칙은 항상
하나로 정해진다.

표시 순서는 이와 별개로 사용자가 정한 순서를 그대로 쓴다. 우선순위와 표시 순서를 분리했으므로 파일이
어느 그룹에 들어갔는지는 파일마다 적용된 규칙으로 확인할 수 있게 한다.

### 5. 잘못된 규칙은 무시하지 않고, 나머지로 그룹화는 계속한다

부분 결과를 우선한다는 기존 원칙을 규칙에도 적용한다. 규칙 하나가 잘못되었다고 Config View 전체를
막지 않는다. 유효한 규칙으로 그룹을 만들고, 잘못된 규칙은 원인과 다음 행동을 함께 표시한다.

검증 대상은 다음과 같다.

| 대상 | 판정 |
|---|---|
| 빈 prefix, 공백만 있는 prefix | 무효 |
| 절대 경로, 드라이브 문자, `..`를 포함한 prefix | 무효 |
| 이미 있는 prefix와 같은 규칙 | 무효 |
| 빈 그룹 이름 | 무효 |
| 이미 있는 그룹 이름과 같은 규칙 | 무효 |
| 규칙 수가 상한을 넘는 경우 | 상한까지만 적용하고 넘친 사실을 알린다 |

검증은 저장 시점과 읽기 시점 양쪽에서 한다. 보관 파일은 사용자가 직접 고칠 수 있는 위치에 있으므로,
읽을 때 형식이 맞는다고 가정하지 않는다.

### 6. 미분류 그룹은 규칙이 아니라 불변식이다

어떤 규칙에도 걸리지 않은 파일은 별도 그룹에 모아 항상 마지막에 표시한다. 이 그룹은 사용자가 지우거나
순서를 바꿀 수 없다. 그룹에 속한 파일 수의 합은 항상 변경 파일 전체 수와 같아야 하며, 이 불변식을
테스트로 고정한다. 문제 파일과 바이너리 파일도 같은 규칙으로 묶이고 문제 상태는 그대로 표시한다.

미분류 파일이 하나도 없으면 그 그룹은 표시하지 않는다.

### 7. 규칙이 없어도 Config View는 선택할 수 있다

규칙이 없을 때 토글을 비활성으로 만드는 방법을 검토했다. 그러면 규칙을 처음 만들려는 사용자가 진입점을
찾지 못한다. Config View는 항상 선택할 수 있게 두고, 규칙이 없으면 무엇을 설정해야 하는지와 규칙을
만드는 방법을 그 자리에서 안내한다.

### 8. 보관 파일을 읽지 못하면 덮어쓰지 않는다

보관 파일이 깨졌거나 읽을 수 없으면 빈 규칙으로 초기화해 덮어쓰지 않는다. 사용자가 애써 만든 규칙을
조용히 지우는 결과가 되기 때문이다. 원인과 다음 행동을 표시하고, 그 상태에서도 Tree View와 List View는
평소대로 쓸 수 있게 한다.

## Risks / Trade-offs

- [저장소를 다른 경로로 옮기거나 다시 clone하면 규칙이 비어 보인다] → 경로가 키라는 점을 규칙 편집
  화면에서 드러내고, 규칙 없음 안내에 현재 저장소 경로를 함께 표시한다. 경로 이동 시 규칙 이전은 이
  change의 범위 밖이며, 필요하면 후속 이슈로 다룬다.
- [prefix만으로는 `*.spec.ts` 같은 규칙을 만들 수 없다] → 이슈가 정규식과 glob, 확장자 규칙을 제외
  범위로 명시했다. 미분류 그룹이 있으므로 못 묶은 파일이 사라지지는 않는다.
- [규칙이 많아지면 그룹이 잘게 쪼개져 오히려 읽기 어려워진다] → 규칙 수에 상한을 두고 상한 도달을
  알린다. 그룹 접기로 화면을 줄일 수 있게 한다.
- [보기가 셋으로 늘어 토글이 좁아진다] → 세 보기 모두 아이콘과 접근 가능한 이름을 유지하고, 선택
  상태를 보조 기술에 계속 제공한다. 이슈 #33이 Full Tree를 더하면 같은 토글을 다시 손봐야 하므로,
  보기 목록을 자료로 선언해 보기 추가가 토글 구현을 바꾸지 않게 한다.
- [규칙 저장이 앱이 처음으로 사용자 데이터를 쓰는 지점이다] → 쓰기 대상 경로를 앱 사용자 데이터
  디렉터리 안으로 한정하고, 요청받은 값에서 경로를 만들지 않는다. 저장 실패도 진단으로 돌려준다.

## Migration Plan

기존 사용자 데이터가 없다. 첫 실행에서 보관 파일이 없으면 규칙이 없는 상태로 시작하고, 규칙을 처음
저장할 때 파일을 만든다. 되돌려야 하면 Config View 토글을 제거해도 Tree View와 List View는 영향을
받지 않는다.
