## Context

결과 계산은 비교 기준에서 시작한 임시 clone에 선택 커밋을 `cherry-pick --no-commit`으로
차례로 적용한다. 지금은 충돌이 나면 `SelectionError("COMMIT_APPLY_CONFLICT")`를 던져
계산 전체를 중단한다.

구현 전에 Git의 충돌 시 index 상태를 실측해 확인했다.

```text
cherry-pick --no-commit <충돌 커밋>   → 종료 코드 1
git diff --cached --name-status        → M clean.txt   (깔끔한 변경은 스테이징됨)
                                         U shared.txt  (충돌 경로만 unmerged)
git checkout --ours -- shared.txt
git add shared.txt                     → unmerged 해제, 적용 직전 내용으로 복구
git cherry-pick --quit                 → index 유지하고 sequencer 상태만 정리
git cherry-pick --no-commit <다음 커밋> → 정상 적용
```

즉 충돌은 커밋 단위가 아니라 경로 단위로 격리할 수 있다. 이 관찰이 이 설계의 근거다.

## Goals / Non-Goals

**Goals:**

- 충돌 경로만 문제로 기록하고 나머지 변경을 결과에 유지한다.
- 문제가 생긴 뒤에도 남은 선택 커밋을 계속 적용한다.
- 결과를 완전한 결과와 부분 결과로 구분한다.
- 문제 파일의 원인, 관련 커밋과 다음 행동을 제공한다.
- 계산 후 임시 작업 공간에 병합되지 않은 상태를 남기지 않는다.

**Non-Goals:**

- 충돌 해결 편집과 사용자가 내용을 고르는 병합 UI.
- 충돌 내용(양쪽 버전)을 나란히 보여주는 3-way 화면.
- 문제 파일을 자동으로 해결하려는 시도.

## Decisions

### 결정 1: 충돌은 경로 단위로 격리한다

충돌이 나면 `ls-files --unmerged`로 충돌 경로를 얻고, 그 경로만 적용 직전 상태로
되돌린 뒤 sequencer를 정리하고 다음 커밋으로 넘어간다.

- **근거**: 위 실측대로 Git이 깔끔한 변경을 이미 스테이징해 두므로, 충돌 경로만
  되돌리면 그 커밋의 나머지 변경이 결과에 남는다. 커밋 단위로 버리면 멀쩡한 변경까지
  잃는다.
- **대안**: 충돌 커밋 전체를 건너뛰기 → 같은 커밋의 무관한 파일 변경까지 사라져
  결과가 사용자의 선택과 크게 달라져 기각.

### 결정 2: 되돌리기는 두 단계로 한다

충돌 시점에는 stage 2("ours")가 적용 직전 내용이므로 `checkout --ours` 후 `add`로
복구한다. stage 2가 없으면(적용 직전에 파일이 없던 경우) index에서 그 경로를 제거한다.
이 단계는 뒤 커밋을 계속 적용할 수 있게 만드는 것이 목적이다.

모든 커밋을 적용한 뒤, 문제 경로를 비교 기준 상태로 한 번 더 되돌린다. 기준에 있던
경로는 기준 내용으로 복구하고, 기준에 없던 경로는 index와 작업 공간에서 제거한다.

- **근거**: 부분 결과는 "문제 파일을 건드리지 않은 상태"여야 신뢰 범위가 명확하다.
  충돌 표시자가 담긴 내용이나 한쪽 버전을 임의로 남기면 사용자가 잘못 판단한다.
- **두 단계로 나눈 이유**: 충돌 시점의 복구만으로는 앞선 커밋이 그 경로에 남긴 변경이
  결과에 남는다. 그러면 문제 파일이 변경 파일 목록과 통합 diff에 정상 파일처럼 나타나
  결정 3과 어긋난다. 마지막에 기준으로 되돌리면 파일 목록과 diff가 자동으로 일관된다.
- **대안**: diff 명령에 문제 경로 제외 pathspec을 주는 방식 → 결과를 만드는 명령마다
  같은 제외 목록을 반복해야 하고 빠뜨리면 어긋나므로 기각.

### 결정 3: 한 번 문제가 된 경로는 계속 문제로 남긴다

문제로 기록된 경로를 뒤의 커밋이 다시 변경해도 그 경로는 문제 파일로 유지하고 결과
파일로 제공하지 않는다.

- **근거**: 앞선 변경이 빠진 상태에 뒤의 변경만 얹으면 어느 선택과도 일치하지 않는
  내용이 된다. 신뢰할 수 없는 내용을 정상 파일로 보여주는 것이 가장 위험하다.
- **대안**: 뒤 커밋이 깔끔히 적용되면 정상으로 승격 → 위 이유로 기각.

### 결정 4: 결과는 문제 파일 목록으로 부분 여부를 표현한다

결과에 `problemFiles`를 추가하고, 이 목록이 비어 있지 않으면 부분 결과다. 별도의
불리언 플래그를 두지 않는다.

- **근거**: 상태를 두 곳에 저장하면 어긋날 수 있다. 목록 자체가 곧 상태다.
- **대안**: `isPartial` 플래그 추가 → 목록과 동기화해야 하는 불변식이 생겨 기각.

### 결정 5: 계산 가능한 파일이 없으면 실패로 유지한다

문제 파일만 남고 정상 변경 파일이 하나도 없으면 결과를 완료로 제공하지 않고 기존
진단 흐름으로 알린다.

- **근거**: 볼 것이 없는 "성공"은 사용자에게 도움이 되지 않는다. 이 경우 필요한 다음
  행동은 선택을 바꾸는 것이며 기존 안내와 같다.

### 결정 6: 문제 파일은 변경 파일 목록에 함께 둔다

문제 파일을 별도 목록으로 분리하지 않고 같은 목록의 경로 순서 위치에 문제 상태로
표시한다.

- **근거**: 원래 위치에서 확인해야 "이 디렉터리의 이 파일이 문제"라는 맥락이 남는다.
  기존 요구사항도 문제 파일을 원래 그룹 위치에 표시하도록 정하고 있다.

## Risks / Trade-offs

- 부분 결과를 완전한 결과로 오인할 위험 → 결과 요약과 파일 목록 양쪽에서 상태를
  구분하고, 문제 파일 선택 시 diff 대신 원인을 표시한다.
- 되돌리기가 실패하면 임시 index에 병합되지 않은 상태가 남을 수 있다 → 되돌린 뒤
  `ls-files --unmerged`가 비었는지 확인하고, 남아 있으면 그 커밋 적용을 실패로 올린다.
- 충돌 종류가 다양하다(내용, 수정/삭제, 추가/추가) → 되돌리기를 stage 2 존재 여부로만
  분기해 종류에 의존하지 않게 한다.
- 기존 실패 흐름에 의존하는 테스트가 있다 → 부분 결과로 바뀌는 시나리오를 명시적으로
  갱신하고, 계산 가능한 파일이 없는 경우의 실패는 유지한다.
