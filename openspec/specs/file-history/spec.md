# file-history Specification

## Purpose
선택한 파일이 대상 브랜치에서 어떻게 바뀌어 왔는지 확인하는 기능의 요구사항을
정의한다. 이력의 범위와 순서, 이름 변경 계보, 통합 결과와의 관계, 커밋별 변경 검토와
복귀, 진입점과 키보드 조작을 다룬다.
## Requirements
### Requirement: 선택 파일 이력 범위와 순서
시스템은 선택한 파일이 대상 브랜치 HEAD에서 도달 가능한 커밋을 거쳐 변경된
이력을 표시해야 한다(SHALL). 다른 브랜치에만 존재하는 커밋은 포함하지 않아야
하며(MUST NOT), 확인한 이력은 오래된 커밋부터 현재 상태 방향으로 표시해야 한다
(MUST).

#### Scenario: 대상 브랜치 파일 이력 표시
- **WHEN** 사용자가 파일을 선택하고 File History를 연다
- **THEN** 시스템은 대상 브랜치 HEAD에서 도달 가능한 해당 파일의 변경 커밋을 오래된 순서로 표시한다
- **AND** 다른 브랜치에만 존재하는 커밋은 표시하지 않는다

#### Scenario: 모든 파일 유형에서 이력 열기
- **WHEN** 사용자가 변경 파일, 변경되지 않은 파일, 바이너리 파일 또는 문제 파일을 선택한다
- **THEN** 시스템은 선택한 파일의 File History를 열 수 있게 한다

#### Scenario: 선택 파일이 없는 상태
- **WHEN** 선택한 파일이 없거나 통합 결과가 준비되지 않았다
- **THEN** 시스템은 File History를 실행할 수 있는 상태로 표시하지 않는다

### Requirement: 지연 조회와 페이지 추가
시스템은 사용자가 File History를 열 때 선택 파일 이력을 처음 조회해야 하며(MUST),
파일 선택만으로 이력을 조회하지 않아야 한다(MUST NOT). 이력은 최대 100개씩
추가하고, 같은 저장소 세션, 대상 HEAD와 파일 계보의 확인된 결과를 재사용해야
한다(MUST).

#### Scenario: 처음 File History 열기
- **WHEN** 사용자가 파일을 선택한 뒤 처음 File History를 연다
- **THEN** 시스템은 선택 파일 이력 조회를 시작하고 진행 상태를 표시한다

#### Scenario: 파일 선택만 변경
- **WHEN** 사용자가 `Changed Files`에서 다른 파일을 선택하고 File History를 열지 않는다
- **THEN** 시스템은 새 파일의 이력을 조회하지 않는다

#### Scenario: 오래된 이력 추가
- **WHEN** 확인할 이력이 100개를 넘고 사용자가 더 불러오기를 실행한다
- **THEN** 시스템은 최대 100개의 이전 이력을 기존 목록에 추가한다
- **AND** 목록의 시간 방향, 현재 포커스와 스크롤 위치를 유지한다

#### Scenario: 확인한 이력 다시 열기
- **WHEN** 저장소 세션, 대상 HEAD와 파일 계보가 바뀌지 않은 상태에서 같은 File History를 다시 연다
- **THEN** 시스템은 확인한 이력과 탐색 위치를 복원한다

#### Scenario: 대상 HEAD 변경
- **WHEN** 대상 브랜치 HEAD가 변경된 뒤 사용자가 File History를 연다
- **THEN** 시스템은 이전 HEAD의 캐시를 현재 이력으로 표시하지 않고 다시 조회한다

### Requirement: 이름 변경 계보
시스템은 Git이 50% 이상의 유사도로 이름 변경이라고 판정한 이전 경로와 현재
경로를 하나의 파일 계보로 연결해야 한다(MUST). 이름 변경 후보는 최대 1,000개까지
판정하고, 연결할 수 없는 경계는 추측하지 않고 표시해야 한다(MUST). 삭제 후 같은
경로에 다시 생성된 파일은 별도 계보로 취급해야 한다(MUST).

#### Scenario: 이름만 변경된 파일
- **WHEN** 선택 파일이 내용 변경 없이 다른 경로로 이름 변경되었다
- **THEN** 시스템은 이전 경로와 현재 경로를 하나의 이력으로 표시한다
- **AND** 이름 변경 커밋과 두 경로를 함께 표시한다

#### Scenario: 이름과 내용이 함께 변경된 파일
- **WHEN** Git이 50% 이상의 유사도로 이름 변경을 판정하고 같은 커밋에서 내용도 변경되었다
- **THEN** 시스템은 두 경로와 내용 변경을 하나의 이력 항목으로 표시한다

#### Scenario: 삭제 후 같은 경로로 재생성
- **WHEN** 과거 파일이 삭제된 뒤 같은 경로에 다른 파일이 생성되었다
- **THEN** 시스템은 현재 선택 파일의 생성 시점에서 계보를 끝낸다
- **AND** 삭제 전 파일을 현재 파일의 이력으로 연결하지 않는다

#### Scenario: 이름 변경 연결 한계
- **WHEN** 유사도 또는 후보 상한 때문에 이전 경로를 이름 변경으로 확인할 수 없다
- **THEN** 시스템은 확인한 지점에서 파일 계보가 시작됨을 표시한다
- **AND** 내용 유사성만으로 이전 파일을 자동 연결하지 않는다

### Requirement: 통합 결과 기여 상태
시스템은 통합 대상으로 선택되어 합성 과정에서 해당 파일 계보를 정상적으로
변경한 커밋을 기여 상태로 표시해야 한다(SHALL). 해당 파일에서 충돌로 제외된
커밋은 기여 상태가 아니라 문제 상태로 표시해야 한다(MUST). 이후 커밋이 같은
내용을 덮거나 되돌려도 정상 적용된 커밋의 기여 상태를 유지해야 한다(MUST).

#### Scenario: 선택 커밋이 파일을 정상 변경
- **WHEN** 통합 대상으로 선택한 커밋이 해당 파일 계보를 정상적으로 변경했다
- **THEN** 시스템은 그 이력 항목을 통합 결과 기여 커밋으로 표시한다

#### Scenario: 선택하지 않은 파일 이력 커밋
- **WHEN** 파일 이력의 커밋이 통합 대상으로 선택되지 않았다
- **THEN** 시스템은 커밋을 이력에는 표시하지만 기여 상태로 표시하지 않는다

#### Scenario: 파일 변경이 충돌로 제외됨
- **WHEN** 선택 커밋의 해당 파일 변경이 합성 중 충돌로 제외되었다
- **THEN** 시스템은 그 커밋을 기여 상태가 아닌 문제 상태로 표시한다
- **AND** 문제 원인과 사용자가 취할 다음 행동을 제공한다

#### Scenario: 이후 변경이 이전 내용을 되돌림
- **WHEN** 정상 적용된 뒤의 선택 커밋이 앞선 커밋의 파일 내용을 덮거나 되돌린다
- **THEN** 시스템은 합성 과정에 정상 참여한 두 커밋을 모두 기여 상태로 유지한다

### Requirement: merge commit 비교 기준
시스템은 통합 대상으로 선택된 merge commit의 파일 변경을 사용자가 지정한 mainline
부모와 비교해야 한다(MUST). 선택하지 않은 merge commit은 첫 번째 부모와 비교하고
그 기준을 표시해야 한다(MUST). 선택한 merge commit에 필요한 mainline 부모가 아직
없으면 파일 변경을 표시하지 않아야 한다(MUST NOT).

#### Scenario: 선택한 merge commit 검토
- **WHEN** 사용자가 mainline 부모를 지정한 선택 merge commit의 파일 변경을 연다
- **THEN** 시스템은 지정한 부모와 merge 결과의 파일 변경을 표시한다
- **AND** 비교에 사용한 부모를 확인할 수 있다

#### Scenario: 선택하지 않은 merge commit 검토
- **WHEN** 사용자가 선택하지 않은 merge commit의 파일 변경을 연다
- **THEN** 시스템은 첫 번째 부모와 merge 결과를 비교한다
- **AND** 첫 번째 부모가 기준임을 표시한다

#### Scenario: mainline 부모가 정해지지 않음
- **WHEN** 사용자가 mainline 부모를 아직 지정하지 않은 선택 merge commit의 파일 변경을 열려고 한다
- **THEN** 시스템은 파일 변경을 표시하지 않는다
- **AND** Commit History에서 기준 부모를 선택하도록 안내한다

### Requirement: 파일 이력 커밋 검토와 복귀
시스템은 사용자가 파일 이력 커밋을 실행하면 파일 이력이 있던 diff 검토 영역에서 해당
커밋의 파일 변경을 읽기 전용으로 표시해야 한다(SHALL). 이 동작은 통합 대상 선택을
변경하지 않아야 한다(MUST NOT). 커밋 변경 내용에서는 파일 이력으로, 파일 이력에서는
선택 결과 diff로 돌아갈 수 있어야 하며(MUST), 선택 결과로 돌아가면 기존 선택 파일,
diff 레이아웃, 스크롤과 커서 위치를 복원해야 한다(MUST).

#### Scenario: 파일 이력 커밋 열기
- **WHEN** 사용자가 파일 이력의 커밋을 실행한다
- **THEN** 시스템은 파일 이력이 있던 검토 영역에 그 커밋 전후의 파일 변경을 표시한다
- **AND** `Changed Files` 목록과 통합 대상 커밋의 체크 상태 및 선택 수를 변경하지 않는다

#### Scenario: 통합 결과로 돌아가기
- **WHEN** 사용자가 파일 이력에서 선택 결과로 돌아간다
- **THEN** 시스템은 이전 선택 파일과 통합 결과 diff를 표시한다
- **AND** 이전 diff 레이아웃, 스크롤과 커서 위치를 복원한다

#### Scenario: 파일 이력 패널 전환
- **WHEN** 사용자가 커밋 변경 내용에서 파일 이력으로 돌아간다
- **THEN** 시스템은 같은 검토 영역에 파일 이력 목록을 다시 표시한다
- **AND** File History의 포커스와 스크롤 위치를 유지한다
- **AND** 선택 파일, 통합 대상 선택과 `Changed Files` 목록은 변경되지 않는다

### Requirement: 바이너리 파일 변경 안내
시스템은 바이너리 파일의 이력과 커밋별 변경 상태를 제공하되 내용을 텍스트로
해석하거나 불러오지 않아야 한다(MUST NOT). 가능한 경우 변경 상태, 경로, 비교
부모와 이전·이후 blob 크기를 표시해야 한다(MUST).

#### Scenario: 바이너리 파일 이력 커밋 열기
- **WHEN** 사용자가 바이너리 파일의 이력 커밋을 실행한다
- **THEN** 시스템은 추가, 수정, 삭제 또는 이름 변경 상태와 비교 기준을 표시한다
- **AND** 확인 가능한 이전·이후 blob 크기를 표시한다
- **AND** 바이너리 내용 비교를 지원하지 않음을 안내한다

### Requirement: 불완전한 이력과 조회 실패
시스템은 얕은 복제에서 확인 가능한 파일 이력을 계속 표시하고 확인 범위, 누락
원인과 사용자가 취할 다음 행동을 함께 제공해야 한다(MUST). Git 객체 누락 또는
손상으로 확인된 결과를 신뢰할 수 없으면 부분 목록을 현재 이력으로 표시하지 않고
문제 범위, 원인과 다음 행동을 제공해야 한다(MUST).

#### Scenario: 얕은 복제의 파일 이력
- **WHEN** 얕은 복제에서 선택 파일의 확인 가능한 이력을 조회한다
- **THEN** 시스템은 확인된 커밋을 시간순으로 표시한다
- **AND** 전체 이력이 아닐 수 있는 범위, 얕은 복제라는 원인과 필요한 이력을 가져오는 다음 행동을 표시한다

#### Scenario: Git 객체 누락 또는 손상
- **WHEN** 필요한 Git 객체가 누락되거나 손상되어 파일 이력을 신뢰할 수 없다
- **THEN** 시스템은 불완전한 목록을 현재 이력으로 표시하지 않는다
- **AND** 실패한 파일 이력 범위, 확인 가능한 원인과 저장소를 복구한 뒤 다시 시도하는 행동을 제공한다

### Requirement: 비동기 파일 이력 격리
시스템은 파일, 비교 범위 또는 저장소가 바뀌면 진행 중인 이전 파일 이력 요청을
취소해야 하며(MUST), 취소되거나 오래된 응답을 현재 화면에 적용하지 않아야 한다
(MUST NOT).

#### Scenario: 조회 중 파일 변경
- **WHEN** 파일 이력 조회 중 사용자가 다른 파일을 선택한다
- **THEN** 시스템은 이전 파일 조회를 취소한다
- **AND** 이전 파일의 늦은 응답을 새 파일의 이력으로 표시하지 않는다

#### Scenario: 조회 중 범위 또는 저장소 변경
- **WHEN** 파일 이력 조회 중 비교 범위나 저장소가 변경된다
- **THEN** 시스템은 이전 세션 또는 범위의 조회를 취소한다
- **AND** 이전 결과와 임시 파일 diff를 현재 화면에 표시하지 않는다

### Requirement: 키보드 파일 이력 탐색
시스템은 키보드만으로 파일 이력 커밋을 이동하고 변경을 열며 파일 이력과 선택 결과로
차례로 돌아갈 수 있게 해야 한다(MUST). 포커스, 기여와 문제 상태는 색상 외의 이름 또는
모양으로 구분해야 한다(MUST).

#### Scenario: 방향키로 커밋 이동
- **WHEN** 사용자가 File History 목록에서 위·아래 방향키를 누른다
- **THEN** 시스템은 이전·다음 커밋으로 포커스를 이동한다

#### Scenario: 처음과 마지막 커밋 이동
- **WHEN** 사용자가 File History 목록에서 Home 또는 End를 누른다
- **THEN** 시스템은 처음 또는 마지막 커밋으로 포커스를 이동한다

#### Scenario: 키보드로 커밋 변경 열기와 복귀
- **WHEN** 사용자가 포커스한 커밋에서 Enter 또는 Space를 누른 뒤 Escape를 두 번 누른다
- **THEN** 시스템은 해당 커밋의 파일 변경을 열고 첫 Escape에서 파일 이력으로 돌아간다
- **AND** 두 번째 Escape에서 선택 결과 diff로 돌아간다
- **AND** 통합 대상 커밋의 체크 상태는 변경하지 않는다

### Requirement: 선택 파일 이력 진입점
시스템은 선택 파일의 커밋 이력을 여는 File History 컨트롤을 `Changed Files` 머리글의
보기 토글 옆에 제공해야 한다(MUST). 이 컨트롤은 보기 토글과 구분되는 컨트롤이어야 하며
(MUST), 보이는 이름과 동작 설명을 제공해야 한다(MUST). 파일을 선택하지 않았으면 사용할
수 없는 상태로 표시하고 필요한 선행 조건을 안내해야 한다(MUST). 이력을 여는 동안
`Changed Files` 목록은 계속 표시해야 한다(MUST).

#### Scenario: 이력 열기 컨트롤 위치
- **WHEN** 선택 결과의 `Changed Files` 패널이 표시된다
- **THEN** File History 컨트롤이 `Changed Files` 머리글의 보기 토글 옆에 표시된다
- **THEN** 이 컨트롤은 보기 토글의 선택 상태를 바꾸지 않는다

#### Scenario: 선택 파일의 이력 열기
- **WHEN** 사용자가 `Changed Files`에서 파일을 선택하고 File History 컨트롤을 실행한다
- **THEN** diff 검토 영역이 선택 파일의 커밋 이력을 표시한다
- **THEN** `Changed Files` 목록과 선택 파일 표시는 그대로 유지된다
- **THEN** 통합 대상 커밋 선택은 변경되지 않는다

#### Scenario: 선택하지 않은 상태의 이력 컨트롤
- **WHEN** 선택 결과가 준비되고 `Changed Files`에서 파일을 선택하지 않았다
- **THEN** File History 컨트롤은 사용할 수 없는 상태로 표시된다
- **THEN** 사용자는 파일을 선택해야 한다는 조건을 확인할 수 있다
- **THEN** 컨트롤을 실행해도 검토 영역과 포커스 대상은 변경되지 않는다

#### Scenario: 선택 결과가 없는 상태
- **WHEN** 선택 결과가 아직 만들어지지 않았다
- **THEN** `Changed Files` 패널과 함께 File History 컨트롤도 표시되지 않는다

#### Scenario: 키보드로 이력 열기
- **WHEN** 사용자가 Tab으로 File History 컨트롤에 포커스하고 Enter 또는 Space를 누른다
- **THEN** 시스템은 선택 파일의 커밋 이력을 열고 이력 목록으로 포커스를 옮긴다

#### Scenario: 이력을 보는 중 다른 파일 선택
- **WHEN** 사용자가 파일 이력을 보는 중 `Changed Files`에서 다른 파일을 선택한다
- **THEN** 검토 영역은 새로 선택한 파일의 선택 결과 diff를 표시한다
- **THEN** 시스템은 새 파일의 이력을 조회하지 않는다
