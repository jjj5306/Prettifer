# Prettifer Pull Request

현재 브랜치의 전체 변경을 검토하고 품질 근거가 포함된 Pull Request를 만든다.

## Workflow

1. 사용자가 자체 리뷰, PR 생성, 병합과 이슈 종료 중 어떤 작업을 요청했는지 확인한다.
2. 저장소 루트의 `AGENTS.md`와 `.github/pull_request_template.md`를 읽는다.
3. 현재 브랜치, 대상 브랜치, 연결된 GitHub 이슈와 OpenSpec change를 확인한다.
4. 기본 브랜치와 현재 브랜치의 전체 diff를 확인한다.
5. OpenSpec 상태와 관련 검증 명령을 실행한다.
6. 아래 자체 리뷰 기준으로 변경사항을 검토한다.
7. 중요한 발견 사항이 있으면 보고하고, 사용자가 변경까지 요청한 범위에서 PR 생성 또는 병합 전에 수정한 뒤 검증을 다시 실행한다.
8. 자체 리뷰만 요청받은 경우 결과를 보고하고 커밋, push, PR 생성, 병합과 이슈 변경을 수행하지 않는다.
9. PR 생성을 요청받았고 커밋되지 않은 관련 변경이 있으면 `$prettifer-commit` 절차를 적용한다.
10. PR 생성을 요청받은 경우에만 현재 브랜치를 원격에 push하고, 템플릿의 모든 항목을 실제 검토 결과로 채워 Pull Request를 생성한다.
11. 사용자가 병합을 요청한 경우 충돌 여부, 필수 상태 검사, 필수 리뷰와 검증 결과를 다시 확인한다.
12. 해결되지 않은 중요한 발견 사항과 실패한 검증이 없을 때 PR을 병합한다.
13. 사용자가 이슈 종료를 요청한 경우 병합 후 연결된 이슈가 닫혔는지 확인하고, 자동으로 닫히지 않았으면 닫는다.

## Self-Review

### Scope and specification

- 이슈 목표, OpenSpec 요구사항과 diff가 일치하는지 확인한다.
- 관련 없는 파일과 동작 변경이 포함되지 않았는지 확인한다.
- 정상 흐름, 경계 조건, 오류와 부분 성공 상태를 확인한다.

### Code quality

- 이름, 함수, 클래스와 모듈의 역할이 명확한지 확인한다.
- 책임 분리, 의존성 방향과 캡슐화가 적절한지 확인한다.
- 도메인 규칙 중복과 불필요한 결합이 없는지 확인한다.
- 재사용성과 유지보수성을 해치는 구조가 없는지 확인한다.
- 사용 언어의 기본 설계 원칙을 준수하는지 확인한다.
- 오류가 진단 가능한 정보와 함께 처리되는지 확인한다.

### Documentation-only changes

- 요구사항 사이의 모순과 정의되지 않은 용어가 없는지 확인한다.
- 이슈 요약과 OpenSpec 상세 명세의 범위가 일치하는지 확인한다.
- 완료 기준과 작업 목록이 검증 가능한지 확인한다.

### Validation

- OpenSpec 검증, 테스트, lint, format, type check와 build 중 적용 가능한 항목을 실행한다.
- 실행하지 못한 검증은 이유와 영향을 PR 본문에 기록한다.

## PR Body

- 변경 요약과 사용자 또는 개발자 영향을 작성한다.
- `Closes #<issue-number>`로 연결 이슈를 기록한다.
- 관련 OpenSpec change와 주요 요구사항을 기록한다.
- 자체 리뷰 항목의 통과 여부와 실제 발견 사항을 기록한다.
- 실행한 검증 명령과 결과를 기록한다.
- 남은 위험과 후속 작업을 기록한다.

## Merge Gate

다음 조건을 모두 충족해야 병합할 수 있다.

- PR diff가 연결 이슈 범위와 일치함
- OpenSpec과 구현 또는 문서가 일치함
- 해결되지 않은 중요한 리뷰 발견 사항이 없음
- 필요한 검증이 통과함
- PR이 충돌 없이 병합 가능한 상태임
- 저장소가 요구하는 상태 검사와 리뷰가 충족됨

조건을 충족하지 못하면 병합하지 않고 원인과 필요한 조치를 보고한다.

## Output

- 자체 리뷰: 발견 사항, 수정 결과, 실행한 검증과 남은 위험
- PR 생성: PR URL, 대상 브랜치, 리뷰 결론과 검증 결과
- 병합: PR URL, 병합 결과와 최종 커밋 ID
- 이슈 종료: 연결된 이슈 번호와 최종 상태
